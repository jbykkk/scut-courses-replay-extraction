## F01：快捷操作会消费无关草稿

**复现：** 输入一个尚未发送的问题、添加一份附件，再点击顶部“今日清单”。实际请求会带上这份附件；成功后，输入框、草稿缓存和待发附件列表被清空。重试旧回答时也会进入同一个发送函数，成功后清空当前附件列表。

**原因：** `send()` 用 `options.attachments || pending.map(...)` 选择附件，并把操作开始时输入框的内容视为可清空的草稿。它不知道调用方是输入框提交、今日清单、旧消息重试，还是回答下方的追问按钮。`today()` 没有显式传空附件列表。

**改进：** 分开 `submitDraft()` 与 `runAction()` 的意图。快捷操作默认无附件、不修改编辑器；只有提交当前草稿才消费与该请求对应的文本和附件快照。请求期间继续输入的新草稿应保留到缓存。旧消息重试只使用旧消息自己的输入。

**验收：** 草稿及附件存在时，点击今日清单、重试旧消息、开始复习、串联知识，都不修改草稿；正常发送草稿成功后，只清理本次提交的内容。

位置：[study-conversation.js](../extension/study-conversation.js#L178) 的 `send()`，以及第 86、167、173 行附近的快捷操作。

## F02：通信失败后的重试不是同一次请求

**复现：** 一条消息提交后模拟响应丢失，再次发送未修改的草稿，两次请求的 `client_id` 不同。后端专项验证中，不同 ID 会执行两次推理；复用原 ID 则直接返回已保存的结果。

**原因：** 前端每次调用 `send()` 都执行 `crypto.randomUUID()`。后端以 `conversation + client_id` 生成消息 ID，只有收到同一个 ID 才能识别已经完成的请求。前端的通信超时不能证明后端执行失败。

**影响：** 当后端已经成功、响应却未到达浏览器时，重试可能重复调用模型、增加对话记录，并重复创建以本次对话为关联的操作。现有单课时跳过策略能减少部分重复工作，但不能替代请求级去重。

**改进：** 第一次提交时持久化消息 ID 和原始请求快照（含课程、用途、附件及复习关联），通信失败后先查询这次执行的状态，再以原 ID 和原请求继续。用户修改问题或主动发送一条新消息时才换 ID。将“正在处理”“执行失败”“响应暂时未收到”分别反馈给用户。

**验收：** 覆盖响应丢失、请求超时、刷新页面、两个页面重试同一消息；同一已完成请求只产生一次推理/操作。旧消息的练习重试也应携带原 `review_id`，避免丢失复习关联。

位置：[study-conversation.js](../extension/study-conversation.js#L184)、[dialogue.py](../assistant_service/study_agent/dialogue.py#L43)、[study_agent/api.py](../assistant_service/study_agent/api.py#L358)。

## F03：暂停复习无法无损恢复

**复现：** 完成一次复习后暂停，条目从“复习安排”消失。再次在原回答下点击“加入复习”，条目重新出现，但 `attempts` 清空、`cycle` 归零。

**原因：** 首页只返回 `active` 的复习；更新接口仅接受 `complete / snooze / pause`，没有 `resume`。`create_review()` 仅复用仍活跃的条目，遇到相同 ID 的暂停条目会写入新的初始状态。

**改进：** “复习安排”中保留“进行中 / 已暂停”筛选；提供“恢复复习”，保留历史作答和间隔。恢复时明确显示下次复习时间，不把暂停期间累计的提醒逐条补发。对已有暂停条目再次点击“加入复习”也走恢复逻辑。

**验收：** 暂停后可查到条目；恢复后历史作答、关联来源和复习次数均保留；重复点击恢复不产生多条记录。

位置：[reviews.py](../assistant_service/study_agent/reviews.py#L18)、[learning.py](../assistant_service/study_agent/learning.py#L53)、[ReviewUpdate](../assistant_service/study_agent/api.py#L69)、[复习列表](../extension/study-conversation.js#L168)。

## F04：任务缺少修改和撤销的完整流程

**场景：** 创建任务时暂时不知道截止日期，之后老师补充了日期；或者耗时估计发生变化。当前任务行只有“记录进度”和“已完成”，没有修改标题、截止日期、预计耗时的入口。误点“已完成”后，条目立即从未完成列表消失，也没有已完成列表或“重新打开”按钮。

**代码确认：** 任务 API 暴露创建与进度更新，前端仅渲染未完成任务。待确认提案的耗时字段却写着“之后可以调整”。底层保留了任务，并非删除数据，但用户缺少恢复和修改的路径。

**改进：** 增加任务详情编辑、已完成筛选与撤销完成。更新截止日期或耗时时，标记相关计划需要重新安排；“实际已用分钟”明确是累计值，避免把本次用时当总用时覆盖。

**验收：** 修改任务不会生成重复任务；撤销完成保留已用时间；旧计划显示需要更新，用户能查看新旧安排的变化。

位置：[study-tools.js](../extension/study-tools.js#L50) 的 `renderTasks()`、第 39 行附近的耗时说明；[任务 API](../assistant_service/study_agent/api.py#L495)。

## F05：统一课件导入、文件身份和版本行为

当前至少有四种入口：对话附件、文件夹资料导入、单课时课件选择、整门课课件上传。它们分别控制来源类型、单课选择和自动匹配，用户却很容易理解为同一个“添加课件”。

有两处具体差异：

- 整门课导入使用文件内容指纹，来源为 `courseware:<文件名>`；对话附件与单课时上传使用 `digest([文件指纹, chunks])`，来源为 `attachment:<附件ID>`。去重又依赖课程与指纹，因此同一文件经不同入口导入可能形成两份活动来源。
- 同一批次的同名文件已在前端拒绝；但先后两批上传内容不同的同名文件时，会使用相同来源名。专项复现确认，后上传文件使前一份来源退出活动列表。旧证据仍保留，但用户没有选择“更新旧课件”还是“另加一份”的机会。

**改进：** 抽出统一资料导入服务，明确区分文件内容身份、逻辑文档身份、版本和课程关联。上传相同内容提示“已存在”；同名不同内容显示“替换为新版 / 作为另一份课件”。统一入口说明“仅用于本次问答”“加入课程资料”“用于本节笔记”的作用范围。

**验收：** 同一个 PDF 经四种入口导入，不出现不可解释的重复；两份同名但不同章节的课件可以同时保留；主动替换后，旧引文可回查、受影响的笔记或匹配结果明确提示更新。

位置：[courseware_api.py](../assistant_service/courseware_api.py#L56)、[lecture_api.py](../assistant_service/lecture_api.py#L65)、[attachments.py](../assistant_service/study_agent/attachments.py#L89)、[storage.py](../assistant_service/study_agent/storage.py#L86)、[courseware.js](../extension/courseware.js#L99)。

## F06：相似页面的能力不一致，缺少直接交接

**场景：** 从桌面打开学习助手，再点“课堂记录 → 导入课程回放”。即使扩展已经安装，本地 `dashboard.html` 仍隐藏导入控件，提示用户回学校页、再从扩展打开课程笔记。与此同时，对话里发起的整课处理已经能够通过浏览器工作队列继续执行。

**代码确认：** 导入界面以 `chrome.runtime.id` 判断能力；本地桥接脚本只发送 `LOCAL_APP_READY`，不是通用的标签页操作接口。另外，桌面通知需要扩展权限；截图索引的页面查询与服务端校验仍只支持校内域名，未覆盖已支持字幕/回放的校外入口。

**改进：** 用“能完成什么”呈现连接状态。桌面导入页可以提交现有浏览器队列支持的任务；需要手动选择课时时，提供一键打开同课程扩展页的交接。缺扩展、未登录、未开课程页分别给一个直接下一步。截图索引的校外支持独立核验，不能只放宽域名就声称已支持。

**验收：** 从桌面、扩展两种入口都能完成同一个回放导入任务；上下文中的课程不丢失；确实必须在扩展中执行的操作有明确且可直接点击的交接入口。

位置：[dashboard.js](../extension/dashboard.js#L271)、[local-bridge.js](../extension/local-bridge.js)、[study-bridge.js](../extension/study-bridge.js)、[study-tools.js](../extension/study-tools.js) 的 `tabs()`、[ingest.py](../assistant_service/study_agent/ingest.py) 的 `validate_visuals()`。

## F07：浏览器后退与应用内返回不一致

**场景：** 课程列表 → 第一节 → 第二节，按浏览器后退，期望回到第一节或课程列表。

**代码确认：** `navigate()` 使用 `history.replaceState()`，没有为这些操作追加历史记录，也没有对应的 `popstate` 路由恢复。筛选条件、搜索词和大部分详情标签页状态没有写入路由。用户只能依靠页面中的“返回课程”。

**改进：** 主动打开课程或课时用 `pushState`；后台刷新及自动跳转到替代版本用 `replaceState`。统一处理 `popstate`，恢复课程、课时、标签页、搜索与筛选。保留已有导图未保存检查，并让被取消的导航真正停止后续状态变化。

**验收：** 后退、前进、刷新、复制课时链接都恢复正确上下文；取消离开未保存导图后，当前课程和详情标签不变。

位置：[dashboard.js](../extension/dashboard.js#L64) 的 `navigate()`、`openLesson()`、`courseButton()`，以及 [mindmap.js](../extension/mindmap.js#L189) 的 `canLeave()`。

## F08：课程应有稳定身份，名称只负责展示

**结构确认：** 课堂记录主要按 `course_id + sub_id` 聚合；学习资料按课程名称精确检索；整课课件匹配又使用 `course_title == course`。文件夹导入甚至需要用户手动填写“与课堂记录使用同一个课程名称”。

**风险场景：** 学校课程叫“操作系统（A班）”，用户把 PDF 归到“操作系统”；或不同学期有同名课程。前者可能查不到关联资料，后者可能在以名称为键的学习功能中混在一起。这是数据模型风险，本轮没有用真实个人课程验证发生频率。

**改进：** 引入稳定的内部课程 ID，保存学校课程 ID、学期、显示名和用户别名。导入时选择已有课程；首次遇到近似名称时建议关联，由用户确认。迁移不能仅按同名自动合并，需保留历史引用的可追溯性。

**验收：** 修改显示名称不影响检索和课件匹配；别名能指向同一课程；同名不同学期保持隔离。

位置：[library-core.js](../extension/library-core.js) 的 `lessons()` / `groups()`、[storage.py](../assistant_service/study_agent/storage.py#L108)、[courseware_api.py](../assistant_service/courseware_api.py#L35)、[study.html](../extension/study.html) 的文件夹导入表单。

## F09：今日清单和入口命名需要符合实际动作

顶部“今日清单”实际立即发送固定消息“今晚只有30分钟，先学什么？”，并不是打开现有清单。该动作也不读取复习偏好中的每日时间。30 分钟可以是首次默认值，但需要在操作前可见、可修改。

建议使用简短的时间选择入口，展示“今天可用 15 / 30 / 60 分钟、自定义”，记住上次选择；已有清单先展示，再提供重新安排。页面中的“课堂记录 / 课程笔记”“学习伙伴 / 学习工作台 / 学习助手”也应建立统一命名表，避免相同链接看起来像不同功能。

位置：[study-conversation.js](../extension/study-conversation.js#L173)、[study.html](../extension/study.html)、[dashboard.html](../extension/dashboard.html)、[learning.py](../assistant_service/study_agent/learning.py#L48)。
